# Alfaeq GAIA Integration\n\nDate: 2026-09-29\n\n## Decision\nThe GAIA repository is a useful engineering control-plane reference, not a Flutter runtime dependency. License: MIT.\nWe adopt its architecture patterns, not a wholesale copy of the Python/Claude/OpenCode plugin.\n\n## Adopted patterns\n\n### 1. Specialist-agent contracts\nAutonomous Alfaeq tasks should produce a machine-readable execution record: task/event id, requested action, specialist/worker, inputs, actions attempted, changed objects, verification, final state, and failure reason.\nThis complements automation_events and ai_tasks; it does not replace operational domain records.\n\n### 2. Deterministic execution tiers\n- T0 — read: inspect logs, schemas, code, metrics.\n- T1 — validate: lint, static analysis, dry-run, schema checks.\n- T2 — reversible preparation: generate patches, migration plans, test artifacts.\n- T3 — state mutation: production changes require explicit approval.\n- BLOCKED — irreversible/high-risk: never execute through an autonomous worker.\nThe tier is a control decision, not authorization to bypass Supabase RLS or service-role boundaries.\n\n### 3. Memory separation\n- operational truth -> Supabase/Postgres\n- event history -> automation_events\n- AI work state -> ai_tasks\n- engineering knowledge -> repository docs\n- ephemeral worker state -> isolated worker storage\nAuthoritative order, inventory, payment, wallet, and settlement state stays in Supabase.\n\n### 4. Evidence-first completion\nAn agent must not report completion solely from generated text. Completion requires appropriate verification evidence: build/test result, SQL verification, HTTP response, event transition, or artifact/log reference.\n\n## Target flow\nUser/System Event -> Supabase authoritative state -> automation_events -> automation-worker -> n8n/AI specialist -> execution contract -> verification evidence -> verified state transition.\n\n## Safety boundary\nGAIA must not be embedded into the customer-facing Flutter application.\nAgent workers must not bypass RLS/domain functions, mutate inventory outside transactional functions, create real payments for testing, alter wallet/settlement balances outside financial controls, execute arbitrary production commands, or treat model output as authorization.\n\n## Integration sequence\n1. Keep Supabase -> automation-worker -> n8n as the operational event architecture.\n2. Add durable execution contracts when the first autonomous worker needs them.\n3. Add deterministic tier classification at the worker/orchestration boundary.\n4. Add approval records for T3 actions.\n5. Connect JEV/AI workers behind the same gate.\n6. Keep browser and repository agents isolated from production credentials.\n7. Require evidence for autonomous repository changes in CI.\n\n## Outcome\nUse the GAIA model to strengthen Alfaeq as: plan -> specialist -> gated action -> verification -> evidence -> state transition.
